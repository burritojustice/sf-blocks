- **Adding data is three Actions instead of one** (#51): **Add a map layer** (a DataSF dataset, an id, a year), **Add areas** (boundaries to count by) and **Rebuild data** (a map layer or areas by id, the search index, the OSM ways, the street facts). Each asks only for what it needs. The old "Add or refresh data" is now the shared builder they call (`build-data.yml`).
- **A new map layer is built in one run.** The action suggests the fields, the categories (text fields with a few repeating values) and, for points keyed by `cnn`, drawing the streets; writes that as the layer's own file, `data/tiles/sources/<id>.json`; builds it; and opens a pull request with the build report, the field report and preview links (Joiner and Block Party reading the branch).
- **Editing a layer's entry on a pull request rebuilds it** by itself (`rebuild-on-edit.yml`), and the **Check data** check fails when a layer the pull request adds or edits isn't built from its current entry (`index.json` keeps a fingerprint of the entry it was built from, `source`). Layers listed but never built (storm drains, bus stops, High Injury Network, excavation permits) are warnings until someone rebuilds them.
- **No more version conflicts:** pull requests add a note in `changes/<name>.md` instead of editing `VERSION` and `CHANGELOG.md`. After the merge, the **Stamp version** action (`scripts/stamp_version.py`) sets `VERSION`, moves the notes into `CHANGELOG.md` and stamps the changed scripts' first lines. New map layers each get their own file under `data/tiles/sources/`, so they don't conflict in `sources.json` either.
- `build_tiles.py`: `--changed-since <commit>` lists the layers added or edited; `--check --require <ids>`.
